# 软件架构与数据流

本文按当前源码逐层说明固件的启动顺序、任务模型、关键调用链、并发约定与扩展点。
所有参数以 [`App/Inc/arm_config.h`](../App/Inc/arm_config.h) 为准。

---

## 1. 启动顺序

```c
main()
├─ HAL_Init()                       // SysTick + HAL，时基后改用 TIM4
├─ SystemClock_Config()             // HSE 8MHz → PLL → 168MHz
├─ MX_GPIO_Init()                   // 电磁铁 PD12、完成指示 PE9
├─ MX_TIM1_Init() / MX_TIM8_Init()  // CubeMX 占位初始化
├─ MX_USART1_UART_Init() / MX_USART2_UART_Init()
├─ ArmApp_HardwareInit()
│  ├─ BspMagnet_Init()              // 先写关闭电平再切输出
│  ├─ BspPuzzleIndicator_Init()
│  ├─ BspSafetyIo_Init()
│  ├─ ArmButtons_HardwareInit()
│  ├─ ArmServo_Init()               // 先写 HOME 比较值，再启动 PWM
│  ├─ BspUartDma_HardwareInit()     // USART1 + DMA2_Stream2
│  └─ BspDebugUartDma_HardwareInit()// USART2 + DMA1_Stream5
├─ osKernelInitialize()
├─ MX_FREERTOS_Init()
│  ├─ osThreadNew(StartDefaultTask)
│  └─ ArmApp_RtosInit()
│     ├─ BspUartDma_RtosInit()      // 收块队列
│     ├─ BspDebugUartDma_RtosInit()
│     ├─ ArmComm_RtosInit()         // 事件队列 + ArmComm 任务
│     ├─ ArmMotion_RtosInit()       // 运动队列 + ArmMotion 任务
│     ├─ ArmCalibration_RtosInit()
│     ├─ ArmPuzzle_RtosInit()
│     ├─ ArmSafety_RtosInit()
│     └─ ArmButtons_RtosInit()
└─ osKernelStart()
```

要点：

- **队列先于生产者创建**。`ArmComm` 先建立事件队列，运动 / 校准 / 拼图任务才可能投递事件；调度器此时尚未运行，因此不存在竞态。
- **PWM 先装载再启动**。`ArmServo_Init()` 在所有通道写入 HOME 比较值后才 `HAL_TIM_PWM_Start()`，避免上电瞬间先输出默认 1500 μs 再跳到 HOME。
- **电磁铁先写关闭电平再切输出**。`BspMagnet_Init()` 中先 `HAL_GPIO_WritePin(..., 无效电平)` 再配置为推挽输出，防止上电误吸。
- **调零模式**（`ARM_ZERO_CALIBRATION_MODE = 1`）只输出一路固定脉宽，不创建通信 / 运动 / 安全任务；调零完成后必须改回 0。

## 2. 任务与同步对象

| 对象 | 类型 | 深度 | 生产者 | 消费者 |
|---|---|---:|---|---|
| `s_plan_queue` | Queue | 1 | `ArmPuzzle_SubmitPlan`（ArmComm / CLI / 按键） | `ArmPuzzle` 任务 |
| `s_motion_queue` | Queue | 4 | 拼图 / 校准 / CLI / 按键 | `ArmMotion` 任务 |
| `s_event_queue` | Queue | 8 | 运动 / 拼图 / 校准 / 安全 | `ArmComm` → `ArmDebugCli_HandleEvent` |
| `s_request_queue` | Queue | 1 | `ArmCalibration_Start/MoveToPoint` | `ArmCalibration` 任务 |
| UART 收块队列 | Queue | 8 | DMA 空闲中断 | `ArmComm` 任务 |

### 2.1 优先级设计

```text
ArmSafety   48  ← 安全最高，任何时刻可抢占
ArmMotion   40  ← 保证 10ms 插值节拍
ArmComm     32  ← 先发 ACK，再让动作开始
ArmPuzzle   30  ← 提交后阻塞等待完成计数
ArmCalib    30
ArmButtons  28
defaultTask 24
```

`ArmPuzzle` 低于 `ArmComm`，因此「收到帧 → 回 `0xAC`」一定先于机械动作发生，K230 不会因为 ACK 迟到而重发。

### 2.2 阻塞等待而非忙等

`ArmPuzzle_Move()` 在提交运动命令后记录 `ArmMotion_GetCompletionCount()`，随后每 10 ms 检查计数是否变化。运动任务完成一段即自增计数，拼图任务随即继续。这样 CPU 在等待期间让给通信与按键任务。

### 2.3 STOP 的 epoch 语义

```text
Submit: queued_command.stop_epoch = s_stop_epoch   （临界区内快照）
STOP  : s_stop_epoch++，并 xQueueReset(s_motion_queue)
Motion: 取出命令后比较 command.stop_epoch != s_stop_epoch → 直接丢弃并报 STOPPED
插值中: 每步再比较一次，变化即中止
```

即使 STOP 与运动命令在队列操作上交错，也不会出现「STOP 之后仍执行旧命令」的情况。

### 2.4 临界区与 volatile

- `s_busy`、`s_stop_requested`、`s_state`、`s_sequence`、`s_completion_count` 等跨任务字段均为 `volatile`，读写包在 `taskENTER_CRITICAL()` 中；
- 队列本身线程安全，但 `s_busy` 的「检查 + 置位」必须原子，否则两个入口可能同时通过忙判据。

## 3. 接收链路

### 3.1 USART1（视觉）

```text
USART1 RX (PB7)
  → DMA2_Stream2 循环写入 128B 缓冲
  → IDLE 中断：计算本次长度，投递 BspUartRxChunk 到队列
  → ArmComm_Task: BspUartDma_Receive(&chunk, 5ms)
  → ArmPuzzleProtocol_Feed()
       逐字节状态机：AA → 55 → 收满 52 字节
       校验：帧头 / 版本 / COUNT / 帧尾 / offset2..48 累加和 / 坐标范围
       计算 FNV-1a 签名
  → ArmComm_HandlePuzzlePlan()
       检查 s_active_vision_task（必须为 1/2/3）
       混入任务号盐与注入盐
       ArmPuzzle_SubmitPlan()
           签名重复 → DUPLICATE（只回 ACK）
           忙 → BUSY（不回 ACK）
           接受 → 入队
  → BspUartDma_Transmit(0xAC)
```

`BspUartDma_Receive()` 的 5 ms 超时让同一任务还能轮询调试口与事件队列，三个来源在一个任务内串行处理，天然避免解析器共享冲突。

### 3.2 USART2（调试）

```text
USART2 RX (PA3) → DMA1_Stream5 → 队列
  → ArmComm_Task
  → ArmDebugCli_HandleChunk()
       字节流拼行（支持 CR / LF / CRLF，忽略空行）
       超长行报 ERR COMMAND_TOO_LONG
       大写化 → 分词 → 分派
```

CLI 与视觉解析都在 `ArmComm` 任务上下文中执行，因此 `VFRAME` 注入可以安全复用正式解析器。

## 4. 拼图执行链

```text
ArmPuzzle_SubmitPlan()
  ├─ 校验 count ∈ [2,4]
  ├─ 签名去重
  ├─ 忙判据：s_busy || ArmCalibration_IsBusy() || ArmMotion_IsBusy()
  ├─ 置 s_busy / 清 stop
  └─ xQueueSend(s_plan_queue)

ArmPuzzle_Task()
  ├─ ArmPuzzle_PreparePlan()
  │    └─ 逐片 ArmPuzzle_PreparePiece()
  │         ├─ 视觉坐标 → mm
  │         ├─ ArmKinematics_GetBaseYawDeg(pick/place)
  │         ├─ delta = normalize(rotate − (place_yaw − pick_yaw))
  │         ├─ 抓取端 / 放置端相对角分配
  │         ├─ 计算 pick/place 表面 Z（含 trim 与 X 向高度补偿）
  │         └─ SolveBoardPose × 4~5（安全高度 / 表面 / 可选中间高度）
  │              任一点失败 → 返回 IK_UNREACHABLE，整单不执行
  ├─ ArmPuzzle_ExecutePrepared()
  │    └─ 每片：Move(pick_safe) → Move(pick_surface) → Delay → Magnet ON
  │             → Delay → Move(lift_safe) → Move(place_safe)
  │             → Move(place_surface) → Delay → Magnet OFF
  │             → [最后一片：Delay → PE9 脉冲]
  │             → Move(place_safe queued)
  ├─ 回 HOME
  └─ 发布事件 + s_busy = false
```

### 4.1 为什么先预解算

若边做边解，第 3 片不可达会在纸面中途停机，碎片留在半空 / 半途位置，人工恢复困难。
预解算把「可达性」变成整套计划的准入条件，代价只是启动前多算 8～10 个姿态（毫秒级）。

### 4.2 抬升阶段锁定 J2

`ARM_PUZZLE_LOCK_WRIST_AFTER_PICK = 1`：吸合后抬升时把 `pick_lift_safe` / `pick_lift_mid` 的 J2（腕部俯仰）替换为抓取瞬间的角度。
原因是长连杆 + 舵机虚位下，抬升时腕部继续追随高 Z 姿态会把铁片带斜、带滑。到安全高度后的搬运段再恢复正常联动。

### 4.3 时间预算

按默认时长（任务 1/2）单片理论耗时：

```text
1500 + 1200 + 800 + 900 + 2000 + 1500 + 1200 + 1500 + 500 + 1200 ≈ 12.3 s
```

四片约 49 s，加回 HOME 约 50 s；任务 3 使用独立速度参数，约 11.7 s/片。
`ARM_PUZZLE_PLAN_TIMEOUT_MS = 130000` 留出充足余量，同时防止异常死循环。

## 5. 运动链路

```text
ArmMotion_Submit()
  ├─ ArmServo_ValidateAngles()      五路全部在限位内
  ├─ duration ≤ 30 s
  └─ 入队（附 stop_epoch 快照）

ArmMotion_Task()
  ├─ 取命令 → 检查 epoch
  ├─ 记录起始角
  ├─ step_count = ceil(duration / 10ms)
  └─ 每步：
       vTaskDelay(10ms)            相对延时，不追赶绝对节拍
       检查 epoch
       progress = step / step_count
       smooth = 3p² − 2p³          三次平滑（巡边用线性）
       五轴线性插值 → ArmServo_SetAngles()
  └─ 结束时再写一次目标角，确保精确落位
```

**为什么不用 `vTaskDelayUntil`**：若运动任务被高优先级任务延迟，`vTaskDelayUntil` 会连续补跑错过的周期，多个 PWM 目标几乎同时写入，表现为「给了 3000 ms 却突然跳变」。相对延时只会让动作略微变长，不会压缩成危险突跳。

巡边（`ARM_CMD_CALIBRATION_TRACE`）使用线性进度，使相邻 10 mm 小段近似恒速衔接，避免每段起停造成顿挫。

## 6. 逆解调用顺序

`ArmKinematics_SolveBoardPose()` 内部的补偿顺序（与代码一致）：

```text
1. Z 预补偿（XZ 表 / 局部 / 负 Y），当前全为 0
2. for scale = 1.0; scale ≥ 0; scale -= 0.2:
     a. XY 残差网格反算（4 次定点迭代，按 scale 混合）
     b. 单轴反标定表（当前关闭）
     c. 3×3 坐标补偿（当前关闭）
     d. 右半区残差（当前关闭）
     e. 目标 X 偏移（当前 0）
     f. base_yaw = atan2(dy, dx)
     g. 三连杆解析解（负肘优先，再正肘）
     h. 关节角映射 → 五路舵机角 → 限位检查
        成功则返回；失败则降低补偿比例重试
3. 全部失败 → 返回 false（调用方报 IK_UNREACHABLE）
```

> 补偿比例降档的意义：实测补偿会把虚拟目标推远，远角可能因此超出臂展。
> 降档优先保证动作可执行，而不是为了「补偿完整」而拒绝整个点。

## 7. 安全链

| 机制 | 触发条件 | 动作 |
|---|---|---|
| 舵机限位 | 目标角超出 `MIN/MAX_ANGLE_X10` | `ARM_RESULT_ANGLE_LIMIT`，不输出 |
| 运动超时 | 单段等待 > 时长 + 1000 ms | 停止运动，返回 `PLAN_TIMEOUT` |
| 计划超时 | 整套 > 130 s | 停止，关闭电磁铁 |
| 电磁铁超时 | 连续吸合 > 18 s | 停止拼图 / 校准，事件 `MAGNET_TIMEOUT` |
| 急停 | PD13 有效（需 `ARM_ESTOP_ENABLED=1`） | 全部停止，事件 `ESTOP` |
| 通信看门狗 | 2 s 无有效帧（需 `ARM_COMM_WATCHDOG_ENABLED=1`） | 停止，事件 `COMM_TIMEOUT` |
| 手动 STOP | CLI `STOP` / 按键 8 | epoch++、清队列、关电磁铁 |

所有停机路径都会先 `BspMagnet_Set(false)`，避免碎片被吸着不放。

## 9. 扩展点

### 9.1 调整动作速度

只改 `arm_config.h` 中 `ARM_PUZZLE_*_DURATION_MS`（任务 1/2）或 `ARM_PUZZLE_TASK3_*`（任务 3）。每项上限 30000 ms，由 `ArmMotion_Submit` 校验。

### 9.2 增加碎片数量

协议层 `ARM_PUZZLE_PIECE_COUNT` 为 4，帧长随之固定为 52 字节。若改为 3 片，需要同时修改：
`ARM_PUZZLE_PIECE_COUNT`、`ARM_PUZZLE_PACKET_SIZE`、偏移常量（`RECORDS_OFFSET` / `CHECKSUM_OFFSET` / `TAIL_OFFSET`）、`ArmPuzzlePlan.pieces[]` 与视觉端组帧逻辑。

### 9.3 增加关节

1. `ARM_SERVO_COUNT` 加 1，补一组 `ARM_SERVO6_*`；
2. `bsp_servo_pwm.c` 增加定时器通道映射；
3. `arm_servo.c` 的校准表与 `ArmServo_SetPulseUs` 开关；
4. `arm_kinematics.c` 的映射与 `ArmKinematicsSolution`；
5. `arm_motion.c` 插值天然支持任意 `ARM_SERVO_COUNT`。

### 9.4 接入新视觉端

只需实现 USART1 协议：收到 `0x3A/0x3B/0x3C` 后回 52 字节帧；收到 `0xAC` 视为接受。
调试阶段可用 `VFRAME` 手工注入任意合法帧，不必等视觉端就绪。

### 9.5 重新标定

按 [`README.md`](../README.md#8-标定与调试) 的顺序执行；所有标定数据都是 `arm_config.h` 中的宏，不涉及算法改动。

## 10. 编码约定

- 所有对外接口返回 `bool` 或 `ArmResult`，不吞错误；
- 模块前缀统一（`ArmXxx_` / `BspXxx_`），静态函数一律 `static`；
- 魔法数集中在 `arm_config.h`，源码只出现有名字的宏；
- 每处非显然的取舍都留中文注释说明「为什么」，而不是复述「做了什么」。
